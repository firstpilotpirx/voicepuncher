# voicepuncher — AI agent instructions

## What this project is

Push-to-talk voice-to-text menu bar application for macOS Apple Silicon; its command line remains for file mode and development (no terminal setup: a first launch writes the default configuration file). A Cargo workspace of four Rust crates (the application at `app/`, below). Fully offline: two local whisper.cpp speech recognition services — the one for dictation (`whisper-server`, large-v3-turbo q5_0, port 8081, what the app uses) and the one for commands (`whisper-server-commands`, small, port 8085, used only by the command spotting service to confirm utterances) — and a local llama.cpp `llama-server` (Qwen3-4B-Instruct-2507) for text cleanup, all reached over loopback HTTP and running on Metal, plus the command spotting service `voicepuncher-command-spotting` (crate `command-spotting/`, sherpa-onnx keyword spotting confirmed by the speech recognition service for commands) reached over a loopback WebSocket for voice control; in hotkey mode the app starts the services its configuration needs itself, adopts the ones already running and stops the ones it started at quit (`[services] manage`, on by default; off leaves them to the scripts); `just start-model-servers` starts all four (or the named ones) and restarts a service that crashes, until `just stop-model-servers`; each speech recognition service runs as three `whisper-server` copies on the ports 10000 above its own, which the clients find from its address and share through the crate `copy-pool/` (`VOICEPUNCHER_STT_INSTANCES`, `VOICEPUNCHER_COMMAND_STT_INSTANCES`, at most 4). No internet at runtime; loopback connections only.

**Product lifecycle stage:** PoC (Proof of Concept). The core workflow is demonstrated but the codebase is not yet hardened for daily use.

## Repository layout

```
voicepuncher/
  app/          ← Rust menu bar application with a developer command line (hexagonal architecture)
  command-spotting/ ← Rust binary: the command spotting service (voice control)
  copy-pool/    ← Rust library: the copy pool, shared by app/ and command-spotting/
  e2e-test/     ← Rust crate: accuracy benchmark + E2E scenarios
  docs/         ← Architecture documentation + ubiquitous language
  Cargo.toml    ← Cargo workspace (members: app, command-spotting, copy-pool, e2e-test)

```

## Workflow — OpenSpec

Every feature, bug fix and behavior change runs through all stages below, in order — do not skip or reorder a stage. Changes without behavior change (typos, formatting, renames, docs, dependency bumps, tooling) skip stages 1–3 and 6–7 and leave the version unchanged; they still go through a branch, the checks of § How to verify a change, a PR and a merge. When unsure, use OpenSpec.

| # | Stage | How | Done when |
|---|---|---|---|
| 1 | Explore (optional) | `/opsx:explore` | the idea is clear; no files written |
| 2 | Propose | `/opsx:propose "<idea>"` creates every artifact in one go. Artifact by artifact instead: `/opsx:new`, then `/opsx:continue` once per artifact (proposal → specs → design → tasks), or `/opsx:ff` for the rest | `openspec validate <name>` passes and `openspec status --change <name>` shows every artifact done |
| 3 | Approval | show the proposal to the user | the user approved it — **stop and wait**; no code before this |
| 4 | Branch | `git fetch origin && git switch -c <type>/<name> origin/main` (`feat`, `fix`, `chore`) | |
| 5 | Apply | `/opsx:apply`, test-first (§ TDD) | every task in `tasks.md` is checked; `just test` after every edit; one Conventional Commit after every task group; `just check` once, after the last group, when the branch changed a build input |
| 6 | Verify | `/opsx:verify`; then the `spec-test-reviewer` subagent once, only for a change that is not small (`~/.claude/rules-custom/openspec.md`: more than one added or modified requirement, or more than 10 tasks) (§ Gherkin) | no CRITICAL issues; for a reviewed change, `RESULT: PASS` — fix every PARTIAL, CONTRADICTS, UNTRACED, ORPHAN and CONFLICT entry and rerun it only when the fix touched tests or OpenSpec documents |
| 7 | Archive | `/opsx:archive`, then commit | specs merged into `openspec/specs/`, change moved to `openspec/changes/archive/` |
| 8 | Own check | `just check` (from stage 5), only when the branch changed a build input; never `just full-check` on the branch alone | passes on the final commit |
| 9 | Pull request | `git push -u origin HEAD`, `gh pr create` | the PR body lists the checks that ran |
| 10 | Manual run | the user, only when hotkey, recording, overlay, paste or permissions changed (§ How to verify a change) | the user pasted a healthy log |
| 11 | Merge | `kit land` with `run_in_background`: a branch with build inputs joins the landing queue (`landing` in `.claude/kit.yaml`, at most 7 per group); the queue leader merges the group onto `main`, runs one `just full-check` on the combined state and squash-merges every member, splitting a red group until the breaking branch is found; a branch without build inputs lands at once. The session waits for the verdict without polling and does docs or the next change meanwhile; then update the main checkout (below) | the change is on `main` and in the main checkout; when `kit land` sends the branch back, fix the named failure or conflict, rerun the check it names and `kit land` again |
| 12 | Release | `just release` on `origin/main` (§ Release), only when stage 5 bumped the version | the GitHub Release `vX.Y.Z` exists with downloadable artifacts |

- **Listed units only shrink:** a change that touches a unit listed in `app/tests/size_baseline.toml` (§ Architecture rules) shrinks it or leaves it as it is, never grows it; `just test` proves it, and `/opsx:verify` checks that no entry was added or raised.
- **Never leave work uncommitted** (`~/.claude/rules-custom/atomic-commits.md`): commit and push after every finished piece of work, without asking.
- Stages 4–12 are pre-authorized: commit, push, open the PR, squash-merge and release without asking.
- **Filed changes land on `main` at once.** `/create-change`, and any later edit to a change that implements nothing (notes, artifacts, a reworded proposal), ends with a PR squash-merged without asking, then the main checkout update below. `openspec list` on `main` is the backlog; never leave a filed change only on a branch. Stop only at stage 3, stage 10, a failed check you cannot fix, or a scope question the specs do not settle.
- **Update the main checkout after every merge.** The user runs the app from the main checkout (`cargo watch`), not from a worktree, and a merge on GitHub does not change it. `kit land` updates it; after a merge by hand (`gh pr merge`) run `git -C "$(git worktree list | head -1 | cut -d' ' -f1)" pull --ff-only origin main` when that checkout is on `main` and clean; otherwise tell the user it is behind. Say in the report that it is updated.
- A change is not done until stage 11 (or 12, when the version moved) is done. Report which stages ran.

Skills: `/create-change` files a change for later (stages 2–3 only, squash-merged to `main` without asking); `/proceed-change <name>` runs stages 1–12 for one change, stopping only at the gates picked at start. Both skills, the `spec-test-reviewer` agent and the shared OpenSpec rules (generated `opsx:*` skills stay untouched, one session per change) come from agent-kit (`~/.claude/skills/`, `~/.claude/agents/`, `~/.claude/rules-custom/openspec.md`); this file supplies their project values.

**Several changes at once:** `/orchestrate` (agent-kit skill) starts each ready change in a session and worktree of its own, at most 7 at once (`launch.max_running` in `.claude/kit.yaml`) running `/proceed-change`, and a change whose `openspec/changes/<name>/orchestration.yaml` lists `depends_on` only after those changes are archived on `main`; `autonomy` (`auto`, `review`, `explore`) sets how much the change needs the user, and `kit backlog` shows each change as ready, blocked, running, needs you or invalid. A change the user approved when it was filed runs with `autonomy: auto` (`gates=none`): no gate stops it, and its calendar time is its work time; `review` is for a change whose proposal the user has not read, and the audit of 2026-10-16 measured gates and questions at half the calendar time of a change. Limits of this project:

- E2E needs no extra care: the model stages of `check` and `full-check`, and E2E, build and benchmark recipes run on their own, wait for the machine-wide test lock, so parallel changes run them one at a time (§ How to verify a change, Lock classes) (the lock is the GPU's throughput: starting fewer changes at once does not shorten the batch; waiting must cost nothing — a check runs in the background and wakes the session when it ends, never in a polling loop); the builds and unit tests of `check` and `full-check`, `just test` and `just release` do not wait for each other, so coding, builds and tests go on in every session at once — except that the build and test stages (standalone `just test` included) wait out another run's running or waiting model stages, which have the machine alone (§ How to verify a change, Lock classes), at most their hold of about 7 min for a `check` and 16 min for a `full-check`.
- Two changes that bump `version` from the same value conflict in `app/Cargo.toml` when the second merges `origin/main`; that change takes the next version above `main` and corrects the target version in its proposal (`kit version-check`).
- Changes that touch the same code (chunk seams, the command spotting protocol, the same recipe) depend on each other even when no proposal says so: declare it in `orchestration.yaml` when filing the change; the orchestrator does not guess overlaps.

CLI: `openspec list` (changes), `openspec list --specs`, `openspec status --change <name>`, `openspec view` (dashboard), `openspec validate`.

## TDD — Red, Green, Refactor

Every behavior change in stage 5 is test-first (`tdd` skill):

1. **Red** — write the test for the new behavior and run it; it fails because the behavior is missing.
2. **Green** — write the smallest code that makes it pass; `just test` is green.
3. **Refactor** — clean up with every test green.

- **Bug fix:** first write a test that reproduces the bug and watch it fail, before touching the code under test. Commit that failing test on its own (`test: reproduce <bug>` — the commit message states it is intentionally red), then fix it in the next commit. The red commit proves the bug existed; the green one proves the fix.
- A test that passes on its first run proves nothing: change it until it fails for the expected reason, then go green.
- `tasks.md` lists the Red task before the Green task for each behavior.
- At slice, component and E2E level, the Red test is the `.feature` scenario written from the spec (§ Gherkin).

## Gherkin — business tests mirror the specs

Business behavior is tested in Gherkin `.feature` files executed by cucumber-rs, so each test reads like its OpenSpec scenario.

| Test | Form |
|---|---|
| Unit (`#[cfg(test)]`) | plain Rust; never Gherkin |
| Adapter integration (`app/tests/it/<adapter>.rs`), architecture | plain Rust |
| Slice / component (`app/tests/features/{slice,component}/<capability>.feature`) | Gherkin, steps in `app/tests/steps/<capability>.rs`, harness `app/tests/cucumber_integration.rs` |
| E2E (`e2e-test/tests/features/<capability>.feature`) | Gherkin, steps in `e2e-test/tests/steps/<capability>.rs`, harness `e2e-test/tests/cucumber_e2e.rs` |

- One `.feature` per OpenSpec capability, named after it with `-` and `/` → `_` (`file-transcription` → `file_transcription.feature`); `Feature:` is the capability id, one `Rule:` per `### Requirement:`.
- Each `.feature` scenario matches a spec scenario by meaning, not wording (`~/.claude/rules-custom/gherkin.md` § Traceability).
- Tag the feature with its capability (`@file_transcription`) and level (`@component`, `@slice`, `@e2e`); `@wip` scenarios are not run; `@smoke` / `@regression` / `@accuracy` / `@seams` / `@cues` / `@resilience` / `@bundle_engines` pick the E2E subsets `just e2e-smoke` / `just e2e-regression` / `just e2e-quick` / `just e2e-seams` / `just e2e-cues` / `just e2e-resilience` / the `e2e-bundle` stage run. In `voice_control.feature`, `@smoke` keeps 2–3 synthesized scenarios per command and every `@voice_samples` one; the other example rows are `@regression`, which only `full-check` runs; `text_refinement.feature` keeps its 20-run output-limit series `@regression` too, so only `full-check` runs it.
- Steps hold no assertions in `Given`/`When`; types, flags, env vars and file paths live in step code, never in the `.feature` text.
- The `spec-test-reviewer` subagent (`~/.claude/agents/spec-test-reviewer.md`) compares meaning: it reads the change's OpenSpec documents (proposal, specs, design, tasks) and every test in scope — `.feature` scenarios with step code and plain Rust tests — and reports tests that miss or contradict a document, orphan `.feature` scenarios and conflicts between documents. Run it once at stage 6 for a change that is not small, and again only when a fix after it touched tests or OpenSpec documents.

## Release

- **Version:** `version` in `app/Cargo.toml`, SemVer. The proposal states the bump; the last task group of `tasks.md` bumps it. Pre-1.0: breaking change or new capability → MINOR, bug fix → PATCH. Changes without behavior change keep the version and get no release.
- **`just release`** runs after the merge, on a clean checkout of `origin/main` (in a worktree: `git fetch origin && git switch --detach origin/main`). It refuses to run otherwise, and when the tag already exists. It runs `cargo clean`, the tests and the release build from scratch (`_release-package`, without the machine-wide lock: it uses no shared service, port or GPU), then tags `vX.Y.Z`, pushes the tag and creates the GitHub Release with the signed disk image `voicepuncher-vX.Y.Z.dmg` and its `.sha256`; it refuses to run without `VOICEPUNCHER_SIGNING_IDENTITY` naming a code-signing certificate in the keychain (README § Release checklist); release notes are generated from the merged PRs. `cargo clean` deletes `target/release/voicepuncher` and `dist/`, which the user may be running: in the main checkout, ask first.

## How to verify a change

All checks are `just` recipes (see `justfile`; no other scripts). A change is "verified" only when every level that applies has run and passed — say which levels ran and which did not.

| When | Command | What it runs |
|---|---|---|
| After every edit | `just test` (~1 min, without the machine-wide lock) | unit + architecture + integration tests, then `metrics` (below) |
| Once per change, after the last task group and before verify (and after `kit sync-base` when its last line names it) | `just check` (~8.5 min; machine lock held ≈ 7.3 min) | fmt, `lint` (clippy `-D warnings` and the static analyzers, below), `test`, `metrics`, release build, E2E smoke, WER accuracy on 10 samples, refinement evaluation; incremental, the machine lock only for the model stages |
| Once per landing group (`kit land` runs it on the group's combined state), before a release | `just full-check` (~15.5–17.5 min; machine lock held ≈ 14.5 min with 10 recordings, ≈ 16.3 min with 100) | everything in `check` (incremental, no `cargo clean`), plus the rest of the voice control scenarios and the 20-run refinement series (`e2e-regression`), the chunk seams (`e2e-seams`: seam sweep and seam matrix), the start cues (`e2e-cues`: the start cue of each voice start timed on an idle machine, last), the outages (`e2e-resilience`: services paused, killed and restarted while voice control runs, on ports of their own) and the bundled engines (`e2e-bundle`: a copy of the bundle starts every service from its own engines, on ports of its own, with nothing but `/usr/bin:/bin` on `$PATH`, and the engines must run on Metal; `just bundle-smoke` runs the bundle stage and it), with WER accuracy on a fixed sample of 100 recordings when the branch changes the recognition path, else on 10 (below) |
| Before merging a change to hotkey, recording, overlay, paste, permissions | manual run by the user | `README.md` § Release checklist |

**Hosted CI** (`.github/workflows/ci.yml`, GitHub Actions on `macos-15`) runs `just fmt`, `just lint` and `just test` on every pull request and every push to `main`: the floor every PR has, also one opened from another machine. It runs no model, service or E2E stage and sets `VOICEPUNCHER_NO_MACHINE_LOCK=1`, which runs the locked recipes' bodies without the agent-kit lock (absent there) and skips only the lock's own self-test in `just test`. The landing queue's `full-check` stays the merge gate for build inputs; a red CI run is a failure like any other (fix it, never rerun it unchanged).

Build inputs are `app/`, `command-spotting/`, `copy-pool/`, `e2e-test/`, `.config/` (`nextest.toml`), `Cargo.toml`, `Cargo.lock` and `justfile`. A branch that changes none of them (docs, `AGENTS.md`, `openspec/`, `.claude/`) needs `just test` only; never `just check` or `just full-check` for it. A branch that changed a build input lands only through the landing queue: its own `just check` passes, then `kit land` queues it and the group's `just full-check` is the merge gate; `kit land` writes the checks that ran into the PR. A branch behind `main` is not refused and does not rerun a check for that: the group check covers what landed meanwhile. When `kit land` sends a branch back after a conflict, merge `main` with `kit sync-base` and run exactly the check its last line names.

**Static analyzers** (design of `adopt-static-analyzers`), all pinned (`just tools` installs them, `_require-tools` names the install command and installs nothing), all unlocked:

- `just lint`: clippy `-D warnings` (default lints, size budgets); the clippy ratchet (`voicepuncher-analyzers clippy`: `pedantic`, `nursery`, `unwrap_used`/`expect_used`/`panic` outside test code, `undocumented_unsafe_blocks`; lints off for the project and the test paths in `.config/analyzers.toml`); `cargo machete` (unused dependencies); `cargo deny` (`deny.toml`: advisories, licenses, sources; duplicate versions reported only); `cargo +stable semver-checks` of `copy-pool` against `origin/main`; `typos` (`.typos.toml`); shellcheck and perlcritic over the recipe bodies (`voicepuncher-analyzers recipes`).
- `just metrics` (a stage of `test`, `check`, `full-check`): the 25 most complex functions and a table per module directory (functions, median and longest length, cyclomatic, `unsafe`/`unwrap`/`clone`, fan-in/out); ratchets every function over cyclomatic 10, the import cycles, `unsafe` per crate and the duplicated lines `jscpd` finds. Cognitive complexity stays gated by the size budgets.
- The ratcheted findings live in `.config/analyzers/{clippy,recipes,metrics}.toml`: a new finding or a grown count fails, a shrunk count passes, a finding gone fails until `just analyzers-baseline` drops it; a rewrite that adds or raises an entry is reviewed like code (after a merge of branches, as `just size-baseline`).

`just bench` is a model comparison, not a gate — only when a model, decoding params or the prompt changed.

- **Models and corpus** are auto-discovered by the `justfile`: each Whisper model by its file name in `~/.voicepuncher/` or `~/.voicepuncher/models/` (`ggml-large-v3-turbo-q5_0.bin` for dictation, `VOICEPUNCHER_WHISPER_MODEL`; `ggml-small.bin` for commands, `VOICEPUNCHER_COMMAND_WHISPER_MODEL`), the text refinement model by its file name too (`Qwen_Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, `VOICEPUNCHER_LLM_MODEL`); a default not on disk fails with "Run 'just models' or set it in .env"; corpus in `e2e-test/corpus/`. The corpus is gitignored, so in a worktree set `VOICEPUNCHER_BENCH_CORPUS` to the main checkout's `e2e-test/corpus`.
- **Lock classes:** the model stages of every `_stages` run (`check`, `full-check`, the E2E recipes) run in one phase with the machine alone (`_e2e-lock`, design of `run-e2e-alone-on-the-machine`): the phase takes the machine-wide lock exclusively, then the *quiet lock* (`<machine lock dir>-voicepuncher-quiet`) exclusively, which the build and test stages of every `_stages` run (fmt, lint, test, metrics, build, bundle, build-e2e; standalone `just test` too; `_quiet-lock`) hold in the shared mode. So two runs' model stages take turns, the other runs' builds and tests end before the first model stage starts and none starts beside it, and builds and tests still run beside each other; `just release` (its own lock directory) and `cargo watch` take no lock, and a start cue over its bound names the busiest processes and the lock holders beside it in its failure. A locked run waits up to 6 h for its lock (`MACHINE_LOCK_WAIT`, default 21600 s in the `justfile`), so it waits out a queue of several sessions' checks instead of giving up after an hour (exit 75) and running nothing. The stage table and the journal (`locks`, class `e2e`) show the wait and the hold.
- **Fail fast:** `check` and `full-check` run their model stages in the order that shows a failure soonest (`check_model_stages`, `full_check_model_stages` in the `justfile`): voice control first, as it fails most, then the short stages before the long Gherkin runs (`e2e-smoke-services`, `e2e-seams` late), and `e2e-cues` after every other; the voice control part lists the `placed_commands` and `voice_forms` test modules first. Each smoke part runs its service binaries beside its Gherkin scenarios in one nextest call (the harness output is printed when it ends), and the slice/component harness shows nextest one test per `Rule:`, so no long feature file bounds `just test`. Both set `VOICEPUNCHER_FAIL_FAST=1`, so a model stage stops at its first failed test or scenario (nextest and cucumber `--fail-fast`); a passing check still runs every test. Standalone E2E recipes and `rerun-failed` report every failure. The variable changes no stage key.
- **Local services:** the E2E recipes start `whisper-server`, `whisper-server-commands`, `llama-server` and `voicepuncher-command-spotting` (`just start-model-servers`) and stop what they started afterwards; `just test` needs no service. The user's services run on ports 8081, 8085, 8080 and 8082; every run under the machine-wide lock (the model stages of `check` and `full-check`, every E2E recipe) starts its own services from the checkout's code and models on test ports 28081, 28085, 28080 and 28082 (`VOICEPUNCHER_TEST_STT_PORT` and siblings), never reuses or stops a service it did not start, restarts one a killed locked run left there, and fails before its first stage, naming the process, when anything else holds a test port; a branch or test that needs services of its own sets `VOICEPUNCHER_STT_PORT`, `VOICEPUNCHER_COMMAND_STT_PORT` and `VOICEPUNCHER_KWS_PORT` together (the `@local_services` and `@resilience` steps pick free ones for all three), so it never starts, reuses or stops a shared speech recognition service; the model stages of `check` and `full-check`, and every build, E2E and benchmark recipe run on its own, wait for the machine-wide test lock (`~/.claude/rules-custom/machine-lock.md`), so runs from parallel checkouts queue instead of colliding; `check` and `full-check` start the services inside the lock and stop them before releasing it. `just test`, `just release` and the stages of `check` and `full-check` before their model stages (fmt, lint, test, build, build-e2e) use no shared service, port or GPU and start at once, beside each other and any locked recipe outside `_stages`, but wait out another run's model stages (Lock classes, above). E2E business scenarios synthesize speech with macOS `say`.
- **Test limits:** every Rust test runs under cargo-nextest 0.9.146 (`cargo +stable install --locked cargo-nextest@0.9.146`); the recipes' guard `_require-nextest` stops with that command when it is missing and installs nothing. Each test has a time limit in `.config/nextest.toml`: 2 min by default, one per E2E suite (a Gherkin harness run is one test). A test over its limit is stopped and reported `TIMEOUT`: it hung — report it, never rerun it unchanged, never raise a limit to let a hang pass. A limit is the smallest whole number of minutes that is at least twice the longest run, never below 2 min; a suite that grows past half its limit gets a new limit, twice its new longest run, in the same change. `VOICEPUNCHER_HANG_PROBE=1 just test` (stopped at 2 min) and `VOICEPUNCHER_HANG_PROBE=1 just e2e-quick` (3 min) prove the limits still work, e.g. after a nextest bump.
- **A flake is a failure; the same worktree:** a test that fails fails the run, whatever it failed on — the load of other sessions' runs, the `[machine-lock]` holder, timing: never rerun it unchanged, not once, and nothing lands on a lucky second run. Fix it in the change when its cause is in scope; otherwise file its fix with `/create-change`, naming the test, the recipe and what ran beside it (other sessions' runs, the `[machine-lock]` holder), and declare that change in `depends_on` of this one, so the branch waits for the fix. No bar is loosened, no test dropped; exit 124 is a hang, reported and never rerun unchanged. Let this worktree's `check` or `full-check` finish before running `just test`, another `check` or `full-check` there: they share `target/`, and the lock no longer keeps them apart.
- **After a fix, rerun only what failed:** commit a fix, then `just rerun-failed` — it takes this worktree's last run from the stage journal and reruns only its failed tests and scenarios, inside the stage they failed in, with that stage's build, services, test ports, machine lock and time limits (seconds instead of the stage's minutes); `just rerun-failed '<package>::<binary> <test>' 'scenario: <name>'` names them by hand. Repeat until it passes, then run the failed stage's recipe (or the check that failed) whole once, so a fix that broke another test is still caught. A rerun is journaled as `rerun-failed` and is never the change's passing check; it fails when a named test never ran. It runs only after a commit that changed something since the failed run, never as an unchanged retry (the flake rule above).
- **The stage journal:** every run of `test`, `check`, `full-check` and the E2E recipes goes through `_stages`, prints its stage table and appends one JSON line to `~/.cache/voicepuncher/stage-times.jsonl` (`VOICEPUNCHER_STAGE_JOURNAL`; failed and interrupted runs too, not a run killed with KILL): recipe, branch, commit, each stage with its time and result, lock wait and hold, the accuracy sample, the failed tests. `just stage-times [7d|2026-10-01]` (default 30 days) summarizes it; use it, not session logs, to tell where test time goes and whether a speed-up worked.
- **Passed stages are reused:** a stage of `test`, `check`, `full-check` or an E2E recipe that already passed on exactly the same inputs, in any worktree of this machine, `main` included, does not run again; the stage table shows it `↺ reused` with the pass it came from (branch, commit, time), and the journal records it `reused`. Its inputs are hashed into a key: the files it reads (the `justfile`'s `stage_inputs`: `openspec/`, `docs/`, `.claude/` and Markdown feed no stage; a file no line names feeds every stage), the toolchain, the `VOICEPUNCHER_*` and build variables, and for the model stages the models, corpus, voice samples and service binaries. When the `test` stage itself runs, it runs only the workspace packages whose part key (`test@<member>`: the package, what Cargo builds for its tests and every file outside the packages) has no pass, and the `justfile` self-tests only when the `justfile` changed (`test@justfile`); the others show `↺ reused`, so an edit under `command-spotting/` runs no `app` test. A reused stage's journal entry carries the seconds of the pass it reused, and `just stage-times` shows the time reuse saved. So `full-check` after a passing `check` on one commit runs only its own stages, and after `kit sync-base` only the stages whose inputs the merge changed run; a docs-only change takes no machine lock at all. The smoke set runs as four stages, one per capability (`e2e-smoke-speech` with every capability that has no part of its own, `-refinement`, `-voice`, `-services`), so a change to one capability reuses the others. Pass records live in `~/.cache/voicepuncher/stage-passes/` (`VOICEPUNCHER_STAGE_PASSES`), written only by a passing stage whose inputs did not change during the run. `VOICEPUNCHER_REUSE_STAGES=0` runs every stage: use it after a change the key cannot see (another program on the `PATH`, a system library), never to retry a failed test unchanged. A file added on a path that feeds only some stages gets its line in `stage_inputs`.
- **Synthesized speech is cached** in `~/.cache/voicepuncher/speech/` (or `VOICEPUNCHER_SPEECH_CACHE`), shared by every checkout and keyed by macOS build, voice, rate, audio format and text: `say` runs once per phrase per machine. Delete the directory to synthesize everything again.
- **The accuracy sample of `full-check`:** 100 recordings when the branch changes a path of `recognition_paths` in the `justfile` (or a Cargo file beyond its version), on `main` itself and when the changed paths cannot be read; else 10. It prints its choice before its first stage (`● accuracy: …`). Force 100 with `VOICEPUNCHER_ACCURACY_SAMPLE=100` (also for `kit verify`: `VOICEPUNCHER_ACCURACY_SAMPLE=100 kit verify before-merge`) after a change outside the repository — a model, `.env`, a service binary. A branch that adds a file on the recognition path adds it to `recognition_paths`.
- **The user's voice:** recordings of the user's own voice commands live in `~/.voicepuncher/voice-samples/` (never committed; README § Testing); the `voice_samples` integration tests and the `@voice_samples` E2E scenarios run on them when they exist. When voice recognition fails for the user, ask for a new recording session there and add it rather than tuning on synthesized speech alone.
- **The manual run cannot happen in an agent sandbox**: it lacks macOS TCC permissions (`permission denied for accessibility`). Ask the user to run the installed app or `cargo run --release -p voicepuncher` (with and without `--no-llm` when refinement changed) and paste the log (the tail of `~/.voicepuncher/logs/voicepuncher.log`: `tail -n 200`, which the app writes however it was started); with `[services] manage = false`, `just start-model-servers` must run first. A healthy cycle logs `pipeline recv Pressed` → `chunk 1 | … transcribed` → `pasting…` → `stop→paste: … total=…ms`; a voice start also logs `voice start: total=…ms …` at its start cue.

## Ubiquitous language

All domain terms are defined in `docs/ubiquitous-language.md`. Read it before naming any type, method, event, or test. The glossary is the contract — code must match it.

## Architecture rules

- Dependency direction: `adapters → core/application → core/domain`. Reverse direction is forbidden.
- Ports (traits) live flat in `app/src/core/application/`.
- No framework imports inside `app/src/core/`.
- Adapter placement: `app/src/adapters/primary/<tech>/` and `app/src/adapters/secondary/<tech>/`.
- **Size and complexity budgets** (kit `quality.md`, R-130–R-135), for production and test code alike: a function at most 40 code lines (neither blank nor comment-only), 5 parameters, nesting 4 and cognitive complexity 15 (clippy: `clippy.toml`, denied in `Cargo.toml` `[workspace.lints]`); a file at most 300 code lines, a struct 12 fields (past a dozen it holds several concepts), a type 35 public members, a module directory 2 000 code lines in its own `.rs` files (about seven files at the file budget). The units over budget on `main` are listed with their measure in `app/tests/size_baseline.toml`, and each listed function carries `#[expect(clippy::<lint>, reason = "size baseline")]`; `just lint` (clippy) and `just test` (`app/tests/it/size_budgets/`) fail on a unit over budget that is not listed, on a listed unit that grew, on one back within budget still listed, and on any other silencing of a budget lint. `just size-baseline` rewrites the file from the code: to drop entries, or to list what a merge of branches written before the budgets brought in; a rewrite that adds or raises an entry is reviewed like code.

- **Unsafe code states why it is sound:** every `unsafe` block and `unsafe impl` carries a `// SAFETY:` comment of at most 3 lines directly above it — the invariant and who upholds it — and a block holds one unsafe operation (clippy `undocumented_unsafe_blocks` and `multiple_unsafe_ops_per_block`, denied in `[workspace.lints.clippy]`; a single `msg_send!`, which expands to two unsafe calls, carries `#[expect(clippy::multiple_unsafe_ops_per_block, reason = "one msg_send!, two unsafe calls inside")]`). Every `unsafe impl Send` or `Sync` is listed with its file and reason in `ALLOWED` of `app/tests/it/unsafe_impls.rs`; `just test` fails on one not listed and on a listed one gone from the code.

## Key constraints

- macOS + Apple Silicon only (Metal GPU, CoreAudio, macOS TCC permissions).
- No internet at runtime; loopback connections only — all inference is local, in separate local services (speech recognition, text refinement, command spotting).
- Three macOS TCC permissions required: Microphone, Accessibility, Input Monitoring.
