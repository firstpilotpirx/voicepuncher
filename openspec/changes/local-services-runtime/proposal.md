## Why

The four local services — the speech recognition service for dictation (`whisper-server`, three copies), the one for commands (`whisper-server-commands`, three copies), the text refinement service (`llama-server`) and the command spotting service (`voicepuncher-command-spotting`) — are started, health-watched, restarted and stopped by `just start-model-servers` / `just stop-model-servers`: bash functions `supervise` (restart after 1 s doubling to 30 s; kill after 3 failed health checks in a row) and `start_service` (PID files in `~/.voicepuncher/run/`, logs in `~/.voicepuncher/logs/BINARY-PORT.log`, 60 s readiness wait). The app itself only connects: `connect_transcriber`, `connect_refiner` and `connect_command_spotter` exit with code 2 when a service does not answer.

A user of the application (installed from a DMG, no Homebrew, no `just`) will never run those recipes. The user asked for a separate component of the application — its own bounded context — that downloads the models (`model-download`), starts the services and routes between their copies (`whisper-copy-pool`); this change is the starting, watching, restarting and stopping. The user also asked that the models not be restarted every time the app restarts during development (`cargo watch` restarts the binary many times a day; the models take 5–20 s to load): the app must adopt services already running on their ports and leave them alone, and own only those it started.

## What Changes

- At launch — after the permissions gate (`permissions-gate-window`) and, later, after the models check (`model-download`) — the app starts every service it needs that is not already answering on its port, with exactly the arguments the `justfile` uses today (`whisper_args`: `-m MODEL --host 127.0.0.1 --port P --inference-path /v1/audio/transcriptions -l auto -t THREADS -bo 1 -nf -sns -mc 0 --vad -vm VAD_MODEL -vsd 2000 -vp 500 -nlp`; llama: `-m MODEL --host 127.0.0.1 --port 8080 -c 4096 -np 1`; command spotting: `--port 8082 --model-dir … --vad-model … --transcription-url http://127.0.0.1:8085/v1`), with the copies on the convention ports of `whisper-copy-pool` (8081 → 18082–18084, 8085 → 18086–18088) and the threads split as the `justfile` does (`cores / copies`, at least 1). The command spotting service is started only when voice control is on.
- Adopt or own: a service whose port already answers (`just start-model-servers` left it warm, or a previous app instance) is adopted — not started, never stopped at quit, still watched; a service the app started is owned — restarted when it exits or stops answering, stopped at quit. An adopted service that goes away is reported (menu: `dictation service stopped — it was started outside the app`) and waited for; the app never starts its own on a port it did not own, so it never fights the `justfile`'s supervisor for a port.
- Supervision per owned service, with the `justfile`'s numbers: readiness within 60 s (TCP for the whisper copies, `GET /health` for llama and the command spotting service); exit → restart after 1 s, doubling to 30 s; 3 failed health checks in a row (every 2 s, after the first success) → killed and restarted; 5 failed starts in a row → the service is marked Failed, shown in the menu with `Retry` and its log, and left alone until Retry. Readiness of the whole runtime = every needed service ready; then the pipeline starts (`restartable-app-runtime`). The dictation pipeline gets the copy list the runtime started (or found) instead of probing (`whisper-copy-pool`).
- Logs: each service's stdout and stderr go to `~/.voicepuncher/logs/BINARY-PORT.log` (the `justfile`'s names), rotated by the writer of `file-logging` (10 MB × 5). The app's log says `services: dictation copy 18082 ready in 6.2 s`, `services: llama-server exited (code 1); restart in 2 s`, `services: adopted command spotting service at ws://127.0.0.1:8082`.
- Menu bar (`menu-bar-presence`): while services start, the status line says `Starting services… (2 of 8 ready)` (copies counted) with the waiting icon; a `Services` submenu lists each service with its state (`Ready`, `Starting`, `Restarting (try 3)`, `Failed — see log`, `Adopted`, `Stopped outside the app`) and the items `Restart` (owned only) and `Open Log`.
- Quit stops every owned service (SIGTERM, 5 s, then SIGKILL; the command spotting service first, then the whisper copies, then llama) and leaves adopted ones running. A second app instance (launched twice) adopts the first one's services; the first instance's quit then stops them from under the second — accepted (open point).
- Config: a new `[services]` section — `manage = true` (false: the app only connects, as today; set by E2E and when a developer wants the `justfile` in charge), `dictation_copies = 3`, `command_copies = 3` (the `VOICEPUNCHER_STT_INSTANCES` / `VOICEPUNCHER_COMMAND_STT_INSTANCES` defaults), `models_dir = "~/.voicepuncher/models"` (where the `justfile` looks too; `~/.voicepuncher/` is searched as a fallback for the old layout), `logs` unchanged. Environment overrides for tests and the `justfile` keep working: `VOICEPUNCHER_WHISPER_MODEL`, `VOICEPUNCHER_COMMAND_WHISPER_MODEL`, `VOICEPUNCHER_VAD_MODEL`, `VOICEPUNCHER_LLM_MODEL`, `VOICEPUNCHER_KWS_MODEL_DIR` (new, the command spotting model folder), `VOICEPUNCHER_SILERO_MODEL` (new), and `VOICEPUNCHER_WHISPER_BINARY`, `VOICEPUNCHER_LLAMA_BINARY`, `VOICEPUNCHER_KWS_BINARY` (new) for the engine paths.
- Engine binaries are resolved in this order: the environment override; the bundle's `Contents/MacOS/engines/NAME/NAME` (`bundled-engines` fills it); `$PATH` (Homebrew in development); for the command spotting service also `target/release/` and `target/debug/` next to the running binary (the `justfile`'s `kws_binary` logic). A missing binary or model file makes the service Failed with the path that was looked for and, in development, the hint `run just models` / `brew install whisper-cpp`.
- File mode (`--input-file`) never starts services (it connects, as today). The `justfile` recipes stay for development and E2E (`start-model-servers`, `stop-model-servers`, the test ports 28081/28085/28080/28082) and now share nothing with the app except the arguments and the port convention; the E2E harness runs the app with `manage = false` (its services are the harness's).
- `openspec/specs/local-services/spec.md` is rewritten so its requirements describe the services' behaviour whoever supervises them (the app in hotkey mode; the scripts in development): restart on exit, stay stopped when stopped, failed start reported, copies, copy death, every copy stopped, hang restart, plus new ones: adopt or own, services shown, logs per service, start order and readiness before dictation.
- Docs: `docs/architecture/overview.md` (the local services component, lifecycle), `docs/architecture/context.md` (the services are children of the app), `docs/ubiquitous-language.md` (Service runtime, Owned service, Adopted service, Service state, Readiness), `docs/project-map.md`, `README.md` § Local services (what the app starts; `manage = false` for the `justfile`), AGENTS.md § What this project is (the app starts the services; `just start-model-servers` keeps them warm in development). Tech matrix (agent-kit PR, section "macOS Desktop"): in-process service supervision with `std::process::Command` and a thread per service (no launchd agents, no `daemonize`, no HAProxy).

Current stage: PoC. Target stage: Prototype (the app runs with no terminal, no `just`, no supervisor outside it).
Scope: the service runtime (use case, ports, process adapter), adopt-or-own, supervision, readiness, logs, menu states, quit, config section, environment overrides, engine and model resolution, the spec rewrite, docs.
Acceptance bar: with no service running and models present, launching the app (from a terminal with Homebrew engines on `$PATH`) starts the eight processes, the menu shows the readiness count, dictation works within 30 s, voice control works; quitting leaves no `whisper-server`, `llama-server` or `voicepuncher-command-spotting` process; with `just start-model-servers` warm, launching adopts them (the log says so), quitting leaves them running; killing an owned llama-server during use restarts it within 2 s (next dictation refined); `just full-check` green (100 recordings: the recognition path changed through the copy list); the user pastes a healthy log of both scenarios.
Out of scope: downloading models (`model-download`: until it lands, missing models are reported with `run just models`); engines inside the bundle (`bundled-engines`); a Services tab in the settings window (`model-download` adds it); changing the `justfile`'s supervision for development.

## Capabilities

### Modified Capabilities

- `local-services`: rewritten as the behaviour of the services whoever supervises them, with the app as the supervisor in hotkey mode: adopt or own; supervision numbers; readiness before dictation; services shown in the menu; per-service logs; quit stops owned services only.
- `menu-bar-presence`: the `Starting services…` status line with the readiness count; the `Services` submenu.
- `app-runtime`: the state Starting services between Waiting for permissions and Ready; Failed when a service cannot start five times.

## Requirements to specify

1. The app starts the services it needs: at launch, each needed service that does not answer on its port is started with the engine's arguments, and dictation starts once every needed service is ready.
2. A service that already answers is adopted: it is not started, it is watched, and it keeps running after the app quits.
3. An owned service that stops is started again: after an exit the service is restarted after 1 s, doubling to 30 s between tries; after three failed health checks in a row it is killed and restarted.
4. A service that cannot start is reported, not retried forever: after five failed starts in a row it is shown as Failed with its log; Retry starts the tries again.
5. Quit stops every owned service: at quit each owned service is terminated (and killed after 5 s), adopted ones are left running, and no owned process remains.
6. An adopted service that goes away is reported and waited for: the menu says it stopped outside the app; the app does not start its own on that port; when it answers again dictation resumes.
7. The services are shown: the menu lists each service with its state and lets the user restart an owned one and open its log.
8. Each service logs to its own file: stdout and stderr of a started service go to `~/.voicepuncher/logs/BINARY-PORT.log`, rotated by size.
9. The services can be left to the scripts: with `manage = false` the app starts nothing and connects as before.
10. A missing engine or model is named: a service whose binary or model file is not found is Failed with the path looked for.

## Implementation guide

1. **Domain and ports.** `core/domain/local_service.rs`: `ServiceKind { Dictation, Commands, Refinement, CommandSpotting }`, `ServiceSpec { kind, binary, args, port, readiness: Tcp | HttpHealth(path), log_file }`, `ServiceState { Stopped, Starting { try }, Ready, Restarting { try, in: Duration }, Failed(String), Adopted, AdoptedGone }`, `Ownership { Owned, Adopted }`. `core/application/local_services/mod.rs`: `ServiceRuntime` with `start_all(specs)`, `stop_all()`, `restart(kind)`, `snapshot() -> Vec<ServiceStatus>`, `observe(observer)`; one supervisor loop per service on its own thread, written as a state machine driven by a `Clock` port (so the backoff schedule is unit-tested with a fake clock) and the ports `ServiceLauncher` (`spawn(spec) -> Child`, `terminate(child)`, `kill(child)`, `try_wait(child)`) and `ServiceProbe` (`tcp_open(port)`, `http_ok(url)`).
2. **Adapters.** `adapters/secondary/localservices/process/mod.rs`: `std::process::Command` with stdout and stderr to the rotating log writer (`file-logging`), `libc::kill(pid, SIGTERM)` for terminate (`libc` becomes a normal dependency, pinned as in dev-dependencies), `Child::kill` for SIGKILL; `adapters/secondary/localservices/probe/mod.rs`: `TcpStream::connect_timeout` (200 ms) and `ureq` GET with a 2 s timeout. `adapters/secondary/localservices/catalog/mod.rs` builds the `ServiceSpec`s from the config, the environment overrides, the engine resolver (order in What Changes) and the model paths (file names of the `justfile`: `ggml-large-v3-turbo-q5_0.bin`, `ggml-small.bin`, `ggml-silero-v5.1.2.bin`, `Qwen_Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, `silero_vad.onnx`, `sherpa-onnx-kws-zipformer-gigaspeech-3.3M-2024-01-01/`).
3. **Runtime integration.** `Runtime::start`: after the gate, `ServiceRuntime::start_all` when `[services] manage`; the runtime state `StartingServices { ready, total }` from the service observer; when all ready → build the pipeline with the copy list (`CopyPool::with_copies(list)` instead of `discover`); a service that becomes not-ready while Ready does not stop the pipeline (the existing failure notices of `keep-services-running` tell the user); `Runtime::stop` → `stop_all` after the pipeline ends.
4. **Menu.** `menubar/macos/`: `Services` submenu rebuilt in `menuNeedsUpdate:` from `snapshot()`; items with tags per kind; `restart:`, `openLog:`; the status line while starting.
5. **Config.** `config.rs`: `[services]` with defaults; `validate` checks copies 1..=8 and that `models_dir` expands; `config/loopback.rs` unchanged.
6. **Spec rewrite** of `local-services` (delta with every requirement modified or added as listed); the `justfile`'s comments point to the spec.
7. **Tests.** Unit: the supervisor state machine with a fake clock, launcher and probe (restart schedule, health-kill, five failures → Failed, adopt decision, stop order); the catalog (arguments equal the `justfile`'s: a test parses the `justfile`'s `whisper_args` line and compares flags, so the two stay in step until the `justfile` delegates to the app); resolver order. Adapter integration `localservices_process_it.rs`: spawn `/bin/sleep`, terminate, kill, log file written; probe against a listener. Component `local_services.feature` (`@component`, mock launcher and probe): the ten requirements. E2E: `just e2e-smoke` gains `@local_services` scenario `The app starts its services and dictates a file`? — no: file mode never manages; instead a scenario that starts the app in hotkey mode on the test ports with `manage = true`, waits for `services: … ready`, checks the processes, quits with SIGTERM and checks none remains (the harness already handles the test ports; the app under test gets `VOICEPUNCHER_*_PORT` and `VOICEPUNCHER_*_BINARY`).
8. **Docs** as listed; the agent-kit tech matrix PR.

Pitfalls: never adopt a port that answers but is not the expected service (check: whisper copies answer `GET /` with HTML containing `whisper`, llama `/health` returns JSON `{"status":"ok"}`, the command spotting service answers `/health`) — a wrong adoption would be silent; `Command` children inherit the app's stdout — redirect both streams to the log file, never to a pipe nobody reads (a full pipe blocks the engine); set the working directory to the models folder for whisper (`-vm` paths are absolute anyway); whisper's Metal init takes seconds — the 60 s readiness is from the `justfile`, keep it; stop order matters: the command spotting service holds connections to the commands copies, stop it first; `SIGTERM` to a process group kills the app too — send to the pid only; a second app instance must not start a second set (adopt); with `manage = false` the old `connect_*` probing (exit 2 when nothing answers) stays until `keep-services-running` semantics apply — in this change `manage = false` behaves exactly as today.

## Open points

- Two app instances: the second adopts the first's services and loses them when the first quits; proposed accept (rare) and log it; alternative: a single-instance lock (`NSRunningApplication` check) — proposed as a follow-up change.
- Health interval and thresholds: proposed the `justfile`'s (2 s, 3 fails, 1 s → 30 s backoff, 60 s readiness, 5 starts).
- Whether an adopted service should be health-watched with a restart by the app when the `justfile` is not supervising it either (an orphan): proposed no, report and wait.
- `models_dir` default: `~/.voicepuncher/models` (the `justfile` already prefers it).
